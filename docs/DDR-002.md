## Task
On September 24, 2026, I delegated a specific fix in `worker.js`: reject submitted entry data when a skill or job-requirement value exceeds 2,000 characters. This implements the FEATURES.md acceptance criterion: “IF a submitted entry exceeds 2,000 characters, THEN THE SYSTEM SHALL reject it with a 400 response and identify that the entry is too long.” `worker.js` was the delegated file; `app.js` was checked to confirm that the user sees the rejection. ## Findings
- Relevant acceptance criterion passed: 1 of 1, the 2,000-character rejection.
- The first `body.text.length > 2000` check did not reject the oversized value in the submitted app flow. The fix parses JSON-encoded entries and checks `userSkills` and `jobText` individually, while still checking plain-text entries. That explains the separate branches in `worker.js` around lines 202-212.
- At review time, I could not fully explain why each branch in `fieldTooLong` was needed; I tested the app manually with a 2,500-character value. The current unit test covers oversized plain text, but does not directly test an oversized field inside a JSON-encoded entry, so that branch still has a test gap.
- In `app.js`, the entries-save path maps every 400 from `POST /entries` to “text too long,” though the Worker can also return 400 for malformed JSON or missing text. The job-suggestions path maps every 400 to the missing-skills message, including other validation errors.
